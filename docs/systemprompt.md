# Rough — системный промпт

Главный закон:

> **НЕХУЙ УСЛОЖНЯТЬ.**

Всё, что мы делаем, должно читаться как Linux и HTML, а не как enterprise-фреймворк.
Любая фича, которую нельзя объяснить одним предложением, — полная хуйня.
Если есть два способа сделать одно и то же — оставляем один, самый простой.

---

## 1. Простота превыше всего

- Движок `rough` — **пустая оболочка**. Вся логика — только в плагинах.
- Никаких абстракций «на вырост», фабрик фабрик и конфигурационных драконов.
- Разработчик не пишет код ради простых вещей — только HTML с одним атрибутом.
- Если решение требует больше трёх сущностей — стоп, ищем проще.

---

## 2. JSON: сначала паттерн, потом данные

JSON должен читаться глазами за секунду. **Никогда не повторяй в каждом элементе
одни и те же ключи.**

### Плохо — миллион повторений одних и тех же обозначений

```json
{
  "/main": [
    { "id": "time", "x": "0%",  "y": "0%",  "w": "10%", "h": "10%", "html": "tiles/time.html" },
    { "id": "plan", "x": "10%", "y": "0%",  "w": "90%", "h": "100%", "html": "tiles/plan.html" },
    { "id": "plan", "x": "10%", "y": "0%",  "w": "90%", "h": "100%", "html": "tiles/plan.html" }
  ]
}
```

### Хорошо — сначала паттерн, потом данные

```json
{
  "паттерн": ["id", "x", "y", "w", "h", "файл"],
  "/main": [
    ["time", "0%",   "0%",  "10%",  "10%",  "tiles/time.html"],
    ["plan", "10%",  "0%",  "90%",  "100%", "tiles/plan.html"],
    ["plan", "10%",  "0%",  "90%",  "100%", "tiles/plan.html"]
  ]
}
```

Правило: **объявил паттерн один раз — дальше только строки данных.** Если паттерн
стандартный и очевидный — можно вообще без него, позиционный массив читается сам.

---

## 3. Вызовы функций — как Linux и HTML

Разработчик не должен писать километры вызова ради простого действия.

### Плохо — «правильно спроектированный» вызов

```html
<button
  id="btn_logging"
  data-action-type="toggle"
  data-target-file="/etc/myapp/app.conf"
  data-target-key="logging"
  data-on-value="1"
  data-off-value="0"
  data-confirm="true">
  Логи
</button>
```

### Хорошо — как в линуксе, один атрибут

```html
<button action="toggle:/etc/myapp/app.conf:logging">Логи</button>
```

- Один атрибут, короткий, двоеточием: `action="имя:аргументы"`.
- `имя` — это команда Linux: `cat`, `tail`, `grep`, `head`, `wc`, `toggle`, `set`, `run`.
- Аргументы — как в консоли: файл, ключ, значение, команда.

Go-сторона тоже короткая:

```go
rough.AddPlugin("restart_nginx", func(in []string, args []string) ([]string, error) {
    // свой код: что угодно, это твой скомпилированный плагин
    return []string{"готово"}, nil
})
```

Всё остальное — за кулисами движка.

---

## 4. Ноль лишней документации

Документация — это **примеры**, а не простыни текста.

- Цель: человек **нативно за полчаса** понимает, как пользоваться.
- Один живой пример важнее трёх абзацев объяснений.
- Если нужно читать мануал, чтобы сделать кнопку — мы провалились.
- Комментарии в коде — по-русски, короткие, «зачем», а не «что» (и так видно).

---

## 5. Базовые плагины — юникс-лайк вызовы

Собираем базовый набор плагинов так, чтобы каждый мог спросить:
«А как это сделать в линуксе?» — и сделать ровно так же тут.

| Вопрос «как в линуксе» | Здесь |
|---|---|
| `cat /var/log/x.log` | `action="cat:/var/log/x.log"` |
| `tail -n 20 /var/log/x.log` | `action="tail:/var/log/x.log"` (последние строки) |
| `tail -f /var/log/x.log` | `<plugin name="tail" source="file:/var/log/x.log" interval="1s"/>` |
| `grep error /var/log/x.log` | `action="grep:error:/var/log/x.log"` |
| `head -n 5 file` | `action="head:file"` |
| `wc -l file` | `action="wc:file"` |
| `sed`-подобная правка строки | `action="line:file:N"` |
| `echo "k=v" >> file` | `action="append:file:key=value"` |
| `ssh user@host команда` | `action="ssh:user@host:команда"`; ключи `~/.ssh` или `-i:ПУТЬ` (нативно в Go) |
| `curl URL` | `action="curl:https://..."` (`net/http`, тело построчно, нативно в Go) |
| `man` / `man ssh` | `action="man"` — список плагинов, `action="man:ssh"` — справка |

Правила для плагинов:

- Имя плагина = имя команды Linux. Поведение = поведение команды.
- Каждый плагин — отдельный саморегистрирующийся Go-пакет.
- Внутри плагина лежит переменная `man_<имя>` — справка (юникс-like man): первая
  строка — краткое описание, дальше использование, аргументы и примеры сложного
  синтаксиса (пайпы, необязательные флаги вроде `-i`). В `init()` она регистрируется
  через `rough.AddMan("имя", man_имя)` рядом с `AddPlugin` — плагин `man` её показывает.
- Всё нативно в Go: **не дёргаем внешние бинарники**, работает в любом контейнере.
- Нет плагина — движок честно говорит «нет такого действия», а не делает вид.

## 6. Плагины — строго через Go-пайпы

Взаимодействие с плагинами — **только** через пайпы, по строгому синтаксису.
Плагин — чистая функция: строки на входе, строки на выходе, экран не трогает.

### «run» запрещён движком

Имя `run` — **зарезервировано и запрещено движком с самого начала**. Никакой
произвольный запуск команд через кнопку невозможен:

- движок отказывается регистрировать плагин-действие с именем `run`;
- движок отказывается выполнять `action="run:..."` с ошибкой;
- плагин `run` в библиотеку не входит.

Правило №1 безопасности: **никогда не давай кнопке выполнять произвольную команду.**
Если команда реально нужна — она должна быть строго зафиксирована в HTML
(whitelist по построению), а не приходить из ввода.

### Единый контракт

```go
// Плагин — юникс-команда: строки на входе, строки на выходе.
type PluginFunc func(in []string, args []string) ([]string, error)
```

- Вход и выход — всегда `[]string` (строки). Плагин не знает про экран и мышь.
- Реестр один: `rough.AddPlugin(name, fn)`.
- `in` — строки с предыдущего шага пайпа (или nil, если плагин первый).
- `args` — аргументы из вызова (`имя:арг1:арг2`).
- Возврат — строки результата и ошибка.

### Строгий синтаксис вызова

- Вызов: `имя:арг1:арг2` — **имя строго до первого `:`**, аргументы строго через `:`.
- Имя — без пробелов и без `:`.
- Пайп-цепочка: `команда1 | команда2` — разделитель `|`, команды в том же формате.
- Если аргументу нужна «палка» — экранируем; `|` всегда только разделитель.

### Поток при клике

```
клик → хит-тест → строка action → реестр разбирает (имя + args)
     → вызывает функцию плагина → плагин делает работу
     → возвращает строки → реестр отдаёт в главный цикл
     → бекенд рисует статус → фронт показывает на экране
```

Плагин никогда не вызывает других плагинов. Их зовёт только реестр по имени.

---

## Правила для кода (коротко)

1. Минимум сущностей. Если можно не добавить тип/функцию — не добавляй.
2. Всё через реестр плагинов: `AddPlugin` (единый тип-пайп).
3. Комментарии и документация — строго на русском.
4. Один файл = одна ответственность, но без дробления на мелочь.
5. Юникс-лайк синтаксис — `имя:аргументы`, никаких длинных key=value хвостов в HTML.
6. Никаких «встроенных» операций в ядре — только пустая оболочка и плагины.

## Коммиты — чтобы не стыдно было гитхабить

GitHub у каждой папки и файла показывает сообщение последнего затронувшего его
коммита. Один гигантский коммит «добавил всё» — значит у всех файлов одна простыня.
Дроби и подписывай нормально, тогда история читается как оглавление.

### Правила

1. **Один коммит — одно дело.** Не мешай движок, плагины, пример и доки в кучу.
2. **Заголовок — до ~60 символов**, начинается с глагола в повелительном наклонении:
   `Добавил`, `Переименовал`, `Убрал`, `Починил`, `Документировал`.
3. **Заголовок отвечает на «что сделано»**, а не «как».
4. **Группируй по папкам**: движок → `engine/` + `rough.go`, плагины → `plugins/`,
   пример → `example/`, доки → `docs/`. Тогда у каждой папки на GitHub своя подпись.
5. **Не пуши мусор**: без `wip`, `тут что-то`, `фикс` — если не можешь объяснить
   в заголовке, значит это не один коммит.
6. **Мелкие правки к уже готовому** — амендим или ребейзь, не плоди «ещё разок»,
   `2`, `3`, `снова`.
7. Если коммит тронул много файлов одной папки — это нормально (одно дело).
   Если тронул три папки разом — это три коммита.

### Как выглядит хорошо

```text
Движок: вёрстка HTML→клетки, конфиг, холст, реестр, цикл, темы, проверка
Плагины: cat, hello, ssh, curl + агрегатор
Пример: живой проект из 4 строк + embed + данные
Тест реестра: регистрация, запрет run, пайпы
Документация: архитектура, демо, системный промпт
```

### Как выглядит плохо

```text
Движок rough: чистый TUI-движок (HTML->клетки, tcell) + плагины в корне plugins/ (cat, hello) + живой пример example/ (4 строки + embed) + документация в docs/
```

Одна простыня на всё → у `engine/`, `plugins/`, `example/` и `docs/` на GitHub
один и тот же текст. Стыдно.

---

Если сомневаешься между «просто» и «правильно по фэншую» — выбирай «просто».
Лучше простой инструмент, которым пользуются, чем правильный, который никто не понял.
