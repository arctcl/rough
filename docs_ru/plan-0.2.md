## Часть 1. Почему Windows вылетает «без логов» и что делать

### 1.1 Установленные по коду причины (диагноз)

1. **recover в `Run` ловит панику ТОЛЬКО в горутине main.**
   В `engine/engine.go` два фоновых потока запускаются через `go func(){...}()`
   **без какого-либо recover**:
   - пул событий: `go func(){ for { evCh <- s.PollEvent() } }()` — главный подозреваемый;
   - телеграфная мышь: `go func(){ ... tm.read(...) ... }()` (актуально на Linux, но
     код должен быть защищён везде).
   Если `s.PollEvent()` паникует внутри tcell (Windows-консоль, ресайз, быстрый
   ввод, мёртвые/составные клавиши, сброс терминала), паника уходит в **эту**
   горутину, процесс умирает, а `recover` из `Run` **не срабатывает** → `crash.log`
   не пишется. Это и есть «молчаливый вылет».

2. **Верхнеуровневый перехват в `Run` — единственный.**
   Логика: «написали в crash.log, вернули ошибку». Но он не покрывает: чужие
   горутины, `os.Exit`/`runtime.Goexit`, аппаратные сбои (segfault), нехватку
   памяти (OOM/выделение на лету в пайпах).

3. **Нет структурированного лога и снятия состояния.**
   Нет `os/signal` (нет грейсфул-шатдауна, нет корректного `s.Fini()` при
   Ctrl+C/SIGTERM), нет `runtime.ReadMemStats` (нет метрик памяти перед крашем),
   нет ротации `crash.log` (перезаписывается, теряется история).

### 1.2 Фреймворк отлова и диагностики (новый)

Предлагаю отдельный пакет `engine/faultlog` (изолированный, без зависимостей
движка, тестируемый): «фрейм, внутри которого отлавливаются память/логи/стек».

**A. Защищённый запуск горутин `GoSafe(name string, fn func())`**
- Оборачивает `go fn()` в `defer recover` → при панике пишет полный дамп
  (значение паники + `debug.Stack()` + дамп ВСЕХ горутин через
  `pprof.Lookup("goroutine").WriteTo`) и помечает движок «упавшим».
- В `Run` заменить оба `go func(){...}()` на `faultlog.GoSafe("poll", ...)`
  и `faultlog.GoSafe("teletype", ...)`.
- Опционально: сторожевой таймер — если горутина событий умерла (канал закрыт),
  логируем и пробуем пересоздать экран/цикл, а не падать.

**B. Глобальный обработчик сигналов `InitSignals(onExit func())`**
- `os/signal.Notify(ch, os.Interrupt, syscall.SIGTERM)`.
- По сигналу: корректно `s.Fini()`, флашим лог, возвращаем код выхода.
- На Windows `os.Interrupt` = Ctrl+C; `SIGTERM` в `golang.org/x/sys/windows` не
  поддерживается — обрабатываем только то, что реально приходит.

**C. Структурированный лог `faultlog.Log` (crash.log + rough.log)**
- Два файла:
  - `crash.log` — только фатальные события (перезаписывается, как сейчас, но с
    таймстампом и стеком всех горутин);
  - `rough.log` — кольцевой (append, максимум N байт): уровень, время, событие,
    метрики памяти — видно историю перед крашем.
- Метрики памяти при каждом логируемом событии и на выходе:
  `runtime.ReadMemStats`: `HeapAlloc`, `HeapSys`, `NumGC`, `NumGoroutine`,
  `LastGC`. Это то, что можно сопоставить с «чит-энджином» (см. 1.3).

**D. Флаг `--tui-debug`**
- `--tui-debug` включает: подробный лог в `rough.log`, и на панике — **паузу**:
  терминал НЕ закрывается сразу, вверху рисуем/печатаем «crash, жми Enter»,
  чтобы можно было подцепить отладчик к живому процессу и снять стек/состояние
  до того, как всё схлопнется.

## Часть 2. Улучшения движка

### 2.1 Переменные (единственная фича из плана)
- **Bash Parameter Expansion (`var%pat`)** — расширение подстановки переменных
  в `engine/vars.go`: `${var%pat}` / `${var#pat}` (усечение суффикса/префикса),
  как в bash. Сначала — только самые ходовые (`%`, `#`), тесты в `testing_vars_test.go`.
- Примечание: `loop` (перебор диапазонов) НЕ трогаем — в v0.2 он вне плана.

### 2.2 Надёжность рантайма
- **Перезапуск tcell-экрана при ошибке** вместо смерти: если `PollEvent` упал,
  пробуем `s.Fini()` + `s.Init()` заново (или возвращаем ошибку с дампом).
- **Защита от гонок**: пометить кандидатов (глобалы `hotzones`, `outputCache`,
  `stateCache`, `curTheme`) — на будущее запуск с `-race` (сейчас нет gcc на
  Windows; оставить TODO на CI).
- **Ограничение вложенности/размера**: защита от глубокой рекурсии HTML и от
  бесконечных пайпов (лимит шагов на действие), чтобы «зависание» не выглядело
  как вылет.

### 2.3 UX / мелочи
- Статус-окно: многострочные ошибки не обрезать молча (скролл уже есть —
  проверить переполнение).
- Примечание: колёсико мыши для прокрутки УЖЕ работает — вне плана.

## Часть 3. Порядок работ и контроль качества

### Порядок (маленькие шаги, каждый — свой коммит)
1. ✅ **faultlog** (пакет + тесты): `GoSafe`, `Log`, `ReadMemStats`-снимок, ротация.
2. ✅ Подключить `GoSafe` в оба `go func` в `engine.go`; тест «паника в горутине →
   пишется дамп, процесс жив».
3. ✅ `InitSignals` + грейсфул `s.Fini()`; тест на `os.Interrupt`.
4. ✅ Флаг `--tui-debug` + пауза при краше.
5. ⏳ (демо-проверка на Windows-терминале: погонять ресайз/быстрый ввод/AltGr — убедиться, что больше не «молчит»).
6. ⏳ Bash Parameter Expansion `%`/`#` в `vars.go` + тесты.
7. ⏳ UX-мелочи (ошибки в статусе) + регресс.

### Критерии приёмки
- На Windows-терминале 20+ минут активной работы (ресайз, ввод, мышь, графика)
  без единого молчаливого вылета; при любом падении — есть дамп в `crash.log` +
  история в `rough.log`.
- `go test ./...` зелёный, `go vet` чистый.
- Новая фича `var%pat` — со справкой `man` и тестами, в агрегаторе.

### Вне объёма (на будущее)
- `-race` в CI (нужен gcc/LLVM).
- Сторожевой подпроцесс-вотчер (полный watchdog с перезапуском извне).
- Сетевой pprof-эндпоинт (движок принципиально без портов — не вводим).
